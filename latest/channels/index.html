    Channel bridge: GitHub issues as the front door¶

    ← Back to README

    The channel bridge runs autocode bridge on the same persistent Linux host as the core. A team member opens an issue with the bridge label; the bridge starts a durable run (it survives the bridge, the terminal and the SSH session). When the run reaches a human gate — Requirements questions, the plan approval, a pause — the bridge posts it to the issue. The requester replies in the issue; the bridge takes exactly the action the status view names. Between gates nobody is needed: the worker plans, builds, tests and reviews on its own, and the finished change comes back as a draft pull request carrying the run's canonical evidence.

    GitHub is the first channel (issue in #2035, a slice of the remote-service roadmap #2022). Slack and Jira adapters follow on the same bridge core; this page is their contract too.

    Set up the host¶

    One trusted persistent Linux host, prepared like any durable-workflow host: systemd user manager 254 or newer with linger already enabled (the bridge never configures the host; modes list --json names the reason when it is missing), a clone of the repository to build in, an engine the runs will use, and a GitHub token with access to read issues and post comments (GITHUB_TOKEN).

    autocode bridge check     # config, project, GitHub token, durable availability
autocode bridge run       # the daemon; one per host (a lock file refuses a second)

    Everything is configured through the environment:

    Variable Meaning
    AUTOCODE_BRIDGE_GITHUB_REPO OWNER/REPO, the single repository this bridge serves.
    AUTOCODE_BRIDGE_PROJECT the persistent checkout to build in (default: the daemon's directory).
    AUTOCODE_BRIDGE_LABEL the label that takes an issue (default autocode).
    AUTOCODE_BRIDGE_ACTORS a JSON array of GitHub logins allowed to steer runs. Replies from anyone else are ignored.
    AUTOCODE_BRIDGE_OPTIONS a JSON array of launch options (engine, models, --test-command). Every human or run action flag is refused here.
    AUTOCODE_BRIDGE_POLL_SECONDS seconds between polls (default 10).
    AUTOCODE_BRIDGE_OPEN_PR 1 to also push the branch and open the draft PR on completion; the default only prepares it.
    AUTOCODE_BRIDGE_OWNED 1 for the explicit no-systemd mode: runs live with the daemon process, as the GitHub Action's runs do. A daemon restart interrupts them; prefer the durable mode on a host that supports it.

    The requester's flow¶

    1. Open an issue describing the outcome you want and add the bridge label. AutoCode takes it, comments to say so, and starts the run.
    2. Answer in a comment when the run asks a question. Each question carries its id and, when they exist, its options; a single open question takes the whole comment, several take ID: your answer lines.
    3. Read the plan it posts — the acceptance criteria, how each will be checked, constraints and permission boundaries. Reply approve to accept it, or reply with what to change (that goes back to the Requirements Gatherer, and the revised plan is posted for a fresh decision). If the run is one of a change set (autocode changeset link), the bridge also posts the other runs. Once every run waits with a complete plan, it posts their plans too, and approve set approves every plan together (change sets in clients). approve still releases this run alone.
    4. Walk away. If the run pauses or a role's model runs out of quota, the bridge posts why and what to reply (resume, or model NAME).
    5. On completion the bridge commits the change on the run's branch and prepares the evidence pull request (and opens it when configured).

    The rules the bridge keeps¶

    The bridge is a client of the task-run interface, exactly like the terminal chat and the headless conformance client:

    • Tokens never leave the host. Every decision is taken against a fresh status view through autocode_taskrun, with the current token read from that view and passed in the child's environment. Issue comments carry questions, options and plan text — never a control token.
    • Free text never approves. Only the exact words approve, approved, y, yes or lgtm at a plan gate count, and only when a complete plan was posted first. Anything else becomes feedback to the planning stage.
    • An approval binds to the plan that was shown. The bridge records the token of the plan it posted; if the plan changed since, the approval is refused and the new plan is posted instead. approve set binds the same way to the change set's plans it posted, and takes only the set approval autocode changeset status names. Words written before a gate was posted can never answer it: each gate remembers which comments it has already consumed.
    • Person-only stops stay person-only. Pauses, retries and blockers are relayed with their reason, and acted on only by an allowlisted actor's explicit reply. Nothing resumes on its own.
    • Refusals are reported, never retried. When the core refuses an action (a stale token, an answer outside the options), the bridge posts the refusal and re-reads the run. A comment the status view cannot act on is posted as a gap to report against the CLI or the view — the bridge works around nothing.
    • One bridge, one action at a time per run. The daemon holds a host lock; each run takes one action per comment, and the durable worker envelope owns every advancing command.

    Between gates the bridge only watches: the run itself runs to its next stop under the durable worker, whether or not the daemon is up (it reconciles from its records when it returns).

    Operating¶

    autocode bridge status [--json] lists every bridged issue, its current gate and its run. Records live under $XDG_STATE_HOME/autocode/bridge (override with AUTOCODE_BRIDGE_HOME), owner-private, outside every task workspace; the per-issue worktrees, run state and the autocode issue records they carry stay in the project's .autocode/issues, so a person can always pick a run up with autocode chat --run-dir ... or autocode issue status N on the host.

    A refused start (durable execution unavailable, a missing engine, a leftover branch) is posted to the issue and recorded with its reason; the bridge does not retry it automatically. Remove the record to let it try again.
