    Work that spans several repositories¶

    ← Back to README

    One AutoCode run changes one repository. Its workspace is one Git tree. The checkpoints, diffs, protected tests and the Builder's declared changes are all bounded to that tree, and a Builder write outside it is treated as a fault.

    That matters when a request needs changes in more than one separately versioned repository. A ticket that adds a field to an API service and records it in a history service is two pieces of work. A run started in the API repository can deliver only the API half.

    Automatic bug fixes from terminal chat¶

    Start autocode chat in the repository where you see the symptom. On a supported Linux host, use an owned chat (the default), set up your coding backend with /connect, then authorize the local Git checkouts AutoCode may use:

    /repos /path/to/order-api
/repos /path/to/history-service
/repos /path/to/tax-service
Submitting an order records the wrong total.

    This catalog is setup, not a list you must add to each bug report. /repos shows it. Chat setup and related runs share one registry; AUTOCODE_HOME can select a shared registry across projects. Checkouts need committed product code, a branch identifying the delivery base, a GitHub origin, Git push authentication, and gh auth login, GITHUB_TOKEN or GH_TOKEN for PR creation. /repos shows authentication readiness. Before creating a worktree, AutoCode checks repository write access and that the local baseline matches the remote delivery branch. Missing checkouts must be made available before their work starts. Parent-folder scanning and remote cloning remain separate catalog work under #2066.

    The Investigator traces the symptom through code. Grounded repository names resolve against registered directory, GitHub or package names. A unique match is selected automatically; ambiguity or missing access stops for your input. Model-supplied paths and URLs do not authorize a checkout. Further discoveries join the same coordination, including A → B → C dependencies absent from the request. Every member works in an isolated, pinned worktree. Original product files remain untouched.

    If the set expands after a member finishes, AutoCode reopens completed peers and shows a fresh cohort approval with the new member. Earlier approvals cannot release implementation against the expanded set.

    Read and approve the displayed member plans. AutoCode retains the selected role routes, efforts and run limits. A configured money cap is shared across sequential launches using the core's known-cost accounting; unknown cost remains unknown. After each member passes its checks, a separate integration Builder derives a joint regression from the symptom and interfaces. Chat displays this plan for approval too; you do not write its test command. Corrections discovered in the integration copies return through member follow-ups and fresh coordinated approval. A failed independent check also returns its diagnostics to a new integration plan, retaining the failed evidence. The limits are 12 repositories and three joint attempts.

    Independent review and runner execution must establish fail-before/pass-after evidence. Integration copies must match the member trees exactly. Missing checks, waivers and individual PASS reports cannot authorize publication. AutoCode commits the checked files, pushes reserved branches and creates linked PRs with exact revisions and the joint evidence binding. Reopening the chat reconciles existing publications; an uncertain result never authorizes a second PR creation. PRs are not merged automatically.

    /pause cancels further coordination and requests a boundary pause from active members, retaining files and existing PRs. The TUI consumes the public coordination contract.

    Manual change sets¶

    • Requirements and the Investigator notice the other repository. When the request or the code they read shows that part of the work belongs elsewhere, the report says so in its workspace_scope. The runner keeps a reported part only when its quote is verbatim in the request or a saved answer, or when it cites a file in this repository that shows it, such as a client of the other service. Other claims are dropped. This includes work discovered while reproducing a bug that the initial request did not mention. The same public scope and ready briefs make that repository available for linking.
    • It asks you before planning. A kept part stops the run with one question. Answer This repository only to plan this repository's part. The plan then lists each other part in its scope exclusions as Not covered: changes in TARGET: WORK, so the approval screen shows what this run will not deliver. To change the request instead, give feedback. To stop instead, leave the question unanswered: the run's status (scope.briefs) holds a ready brief for each repository, this one first, to start a run with in each. A reproduced bug still waits on its unanswered questions. A follow-up with an existing plan also asks about newly discovered external work: an earlier choice cannot cover another turn or different work. Later model reports retain grounded obligations until human feedback permits Requirements to revise the scope. Answering the scope question requires a refreshed plan and its explicit approval.
    • You can link a run in the other repository. autocode changeset link starts a run in a registered project with that repository's ready brief and records the two runs as one change set, which both runs' status shows under scope.linked (Linked runs). Each run still plans, builds and completes on its own.
    • You can approve the linked plans together. autocode changeset status shows every run's plan and one set token, and autocode changeset approve approves them all at once. A plan that changes in any run withdraws the token (Approving the set).
    • You can check the linked runs together. Name an integration command, such as the consumer's tests against the producer's checkout, with autocode changeset check-command. autocode changeset verify runs it once every run is complete. Its evidence identifies the command, execution target, member runs and their code; a change to any of those withdraws it. Replacing the check also clears its previous waiver. A concurrent record change refuses an old result instead of attaching it to a new check. A failed check can reopen the run that diverged, or you can waive that check with a reason. autocode changeset pr-body writes the section each pull request carries, with the merge order (Checking the set together).
    • The terminal chat shows the change set. Its side panel lists the linked runs, and /changeset shows every run and asks before approving the plans together or running the check. /runs groups the chats of one change set (Change sets in clients). VS Code's Run details does the same with one button. On a GitHub issue, the channel bridge posts every run's plan and takes approve set.
    • Component builds stay inside one repository. autocode components builds several components in parallel, but every component worktree comes from the same repository's HEAD, and integration applies their changes to a worktree of that same repository (Parallel tasks and components). It cannot drive two existing sibling repositories.
    • A parent folder is not a multi-repository workspace. If you start AutoCode in a plain folder that holds several repositories, it creates a new, empty project under that folder instead of working in them. If the parent is itself a Git repository with the services as nested repositories or submodules, changes inside them appear to the parent only as a gitlink, so its diffs and test checks do not see them. Treat both as unsupported.

    Walkthrough: a bug reveals another repository¶

    This walkthrough describes explicit changeset commands for callers that manage their own integration check. Terminal bug chats use the automatic flow above.

    Suppose you report “Submitting an order records the wrong total” in order-api. The Investigator finds a call to history-service and reports that its consumer also needs to accept the corrected payload. You did not need to name that repository in the original request. The pause is triggered by the grounded report; it is not a guarantee that a model will discover every dependency.

    1. Use one registry across the repositories. In every terminal used for this change set, choose the same location before starting runs:

    export AUTOCODE_HOME="$HOME/.autocode"
autocode registry location
autocode "Submitting an order records the wrong total" \
  --workspace /path/to/order-api --engine codex --workflow bugfix

    Use your chosen engine consistently; codex here is an example. Without an explicit AUTOCODE_HOME, task startup uses workspace-local registry storage. For runs already created elsewhere, set the shared home and import their existing project roots with autocode registry import /path/to/project. Import reads saved runs and launches no model.

    2. Keep the scope question open while selecting the other checkout. Copy the source run directory from AutoCode's output. Inspect the exact target and ready brief under scope.external_parts and scope.briefs:

    api_run=/absolute/path/to/the/source/run
autocode --run-dir "$api_run" --status --json

    Select an existing committed checkout yourself. The linked run works directly in the selected checkout, so give it a dedicated Git worktree when you want to keep your normal checkout separate:

    git -C /path/to/history-service worktree add \
  -b autocode/history-fix /path/to/history-fix
autocode registry add /path/to/history-fix
autocode registry list
autocode changeset link --run-dir "$api_run" \
  --target history-service --workspace /path/to/history-fix -- --engine codex

    Replace history-service with the exact target the status reported. registry add registers a committed local Git root without a task or model request. It does not clone repositories, change branches or approve code changes. A target that was not reported, or a checkout you have not registered, is refused.

    3. Bring both runs to their plan approval. changeset status lists each run's directory, current need and continuation command. Open each run's chat:

    autocode changeset status --run-dir "$api_run"
autocode --run-dir "$api_run" --chat
# Use the linked run_dir printed by changeset status:
autocode --run-dir /absolute/path/to/the/linked/run --chat

    In the source chat, answer the scope question This repository only. This means this run owns the API side; the linked run owns history's side. Linking itself does not answer the question. Read the exclusions in both plans and make sure their payload fields, examples and acceptance checks agree. Leave individual plans unapproved while preparing approval of the set.

    4. Review and approve the plans together. In the terminal chat use /changeset, or read the CLI's complete plans and run the approval command it prints:

    autocode changeset status --run-dir "$api_run"
# After reading every plan, substitute the token just shown:
autocode changeset approve --run-dir "$api_run" --set-token TOKEN_JUST_SHOWN

    No token is offered while a member still needs answers or planning. The token binds all current plans. An interrupted partial approval holds every Builder; read status again and retry with its current token. After approval, continue each run with its printed next command or autocode resume --run-dir RUN. If history discovers a third repository, link it from history's run in the same way: it joins this set and all current plans need fresh approval.

    5. Name a real check of the combined behavior. The command must exercise both delivered versions. For example, if history has a tests.test_api_contract module that reads the producer checkout from AUTOCODE_CHANGESET_WORKSPACES:

    autocode changeset check-command --run-dir "$api_run" --in history-service -- \
  python3 -m unittest tests.test_api_contract
# Once both runs have completed their own checks:
autocode changeset verify --run-dir "$api_run"
autocode changeset status --run-dir "$api_run"

    Provide that project-specific test; AutoCode does not generate it from the command above. AUTOCODE_CHANGESET_WORKSPACES is a JSON mapping from the target names in changeset status to the actual run workspaces. Read it in the test instead of hard-coding your original checkout. The command runs in the selected member's workspace. A failed check leaves the set unverified; use autocode changeset reopen --run-dir "$api_run" --target history-service when that member needs correction. A waiver requires your explicit reason.

    6. Prepare delivery. Review the merge order and include the generated change-set section in each pull request:

    autocode changeset order --run-dir "$api_run" order-api history-service
autocode changeset pr-body --run-dir "$api_run" --target order-api
autocode changeset pr-body --run-dir "$api_run" --target history-service

    Use the exact target names from status, including the source name. These commands record order and print text; they do not publish or merge pull requests.

    Verification and current limits¶

    The deterministic regressions drive the public CLI/TaskRun interface with offline providers. They test runner behavior, not a live model's ability to discover an arbitrary service dependency.

    Case Coverage
    TUI symptom → A → B → C discovery → fixes → joint regression → three PRs tests/test_coordination_tui_e2e.py: public chat actions, real Git repositories and actual producer/consumer calls, independent fail-before/pass-after proof, offline GitHub publication and cross-links
    Locally passing but incompatible member; lost PR response and reopened chat The same full-flow test requires a revised coordinated plan, a second joint regression, no publication before correction and exactly one PR per repository; changed joint-test bytes withdraw completion
    Missing or ambiguous repository, missing credentials/access, stale approval, cancellation, changed source/remote, exhausted joint retries tests/test_coordinate.py: refusal or bounded correction before launching/publishing; tests/test_control_tokens.py keeps coordination approval tokens out of provider environments
    Initial bug request omits the other repository; Investigator cites a local service client tests/test_bug_questions.py: pause before planning, public registration of a fresh checkout, linked start, reciprocal links, no Builder, explicit local-only answer
    New external work during a follow-up with an existing plan tests/test_scope_question_cli.py: asks again and invalidates earlier authority
    Invalid target or unregistered checkout; stale or interrupted set approval tests/test_changeset_cli.py: rejects unknown members, stale tokens and Builder dispatch after partial approval; retry and explicit standalone release
    A → B → C membership tests/test_changeset_store.py: one canonical set; duplicates and ambiguous legacy overlap refused
    Real producer output disagrees with the consumer expectation tests/test_changeset_delivery_cli.py: real command fails, blocks joint completion, and can reopen the affected run
    Code/check changes, waiver replacement and concurrent check edits tests/test_changeset_delivery.py and delivery CLI tests: old evidence cannot accept a different command or version

    These are focused regressions, not one live, end-to-end multi-service production trial. Bounded live Kilo MiMo/GLM TUI attempts on 2026-10-27 discovered all three fixture repositories but stopped on planning/report validation before builds, joint testing or real PR publication. See the retained qualification evidence and remaining convergence issue #2208. Live end-to-end delivery is not yet verified. The current implementation also has these limits:

    • Discovery depends on the model reporting grounded external work; it does not crawl every repository or automatically clone a missing one.
    • Automatic coordination currently supports owned terminal chats on Linux and local Git repositories containing ordinary files. Symlinks, submodules and durable_local coordination are refused explicitly; saved execution policies are never silently changed.
    • Independent verification also requires preservation evidence from the original combined suite. If that suite cannot collect or supplies no complete passing test evidence, the result remains unverified and bounded retries stop with diagnostics.
    • The manual change-set API leaves linking and the check command to its caller. Automatic TUI coordination supplies them and requires its separate joint gate. A parent folder containing sibling repositories is still unsupported.
    • In the manual change-set API, without a named integration command, verification.done means all individual runs completed. It does not prove the producer and consumer agree. Name the check before treating the overall bug as resolved.
    • Set approval binds member plans; a separately versioned shared-interface contract and the remaining guided onboarding work are tracked in #2066.

    The manual workflow¶

    Without a change set, coordinate the repositories yourself:

    1. Write one brief per repository. Each brief states the shared requirement, the interface both sides agree on (field names, payload examples, an API schema fragment), and that this run owns only this repository's side.
    2. Start a run in each repository, the producer first when one side consumes the other: autocode in each checkout, or autocode --workspace PATH. Or start the other repository's run with autocode changeset link so the two are recorded together.
    3. Read and approve each plan against the same interface. A plan that changes the interface needs the same change in the other repository's plan.
    4. autocode runs --all lists the runs of every registered project, grouped by project, and the terminal chat's /runs and /open switch between them.
    5. Before merging, run the consumer's tests against the producer's branch, and link the two pull requests to each other with the merge order.

    Without a change set, nothing checks that the two halves agree.
