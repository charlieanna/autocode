    CLI reference¶

    ← Back to README

    Use autocode for tasks and its subcommands for related work. autocode --help shows the short command overview; autocode --help-all lists every run option, and autocode COMMAND --help shows that command's options. This reference lists the accepted public flags, including advanced run controls. Role/model selection is in Models; provider setup is in Providers. Every command accepts -h / --help.

    Entry points¶

    Command What it does
    autocode "Your rough idea" The normal entry point. Runs the full plan → approve → build → validate → complete loop (or stops at the next required checkpoint).
    replay RUN --into WORKSPACE/.autocode/runs/NAME Re-drive a saved run offline with recorded provider events and fresh verification checks; see Replay.
    replay RUN --export DIR Export a bounded recording; --recorded-checks on replay simulates historical checks without current completion evidence.
    autocode resume Continue the unfinished run of this project or task worktree (see Which run a command acts on). Never starts a new task. On a paused or blocked run (PAUSED_*, BLOCKED_*, *_REWORK_REQUIRED, RESOLVER_PENDING) it also acknowledges the stop, as --resume-paused does, so the run goes on: no new budget or recovery allowance, though the per-cycle report-repair and resolver attempt counts restart. A design conflict (PAUSED_DESIGN_CONFLICT) is only shown until you edit the design and pass --resume-paused. Its companions (--retry-failed-stage, --grant-recovery N, ...) need no --resume-paused after it. Plain autocode with no task, run from a script or with output redirected, relaunches a running run the same way but only shows a stop; in an interactive terminal it opens autocode chat.
    autocode status The same as autocode --status: read-only status of that run. Command words are recognized wherever they stand among the options; a task whose whole text is resume, status or explain goes after -- (autocode -- status).
    autocode explain The same as autocode --explain: explain the saved run's stop and the offered next command. Reads only; no model call, run lock or workspace changes.
    autocode demo [--directory PATH] Watch an offline sample plan, demo approval, build, rejected evidence and completion acceptance with the bundled fake provider. No account or model spend. Creates a new temporary directory by default, keeps its run and evidence records for inspection, and refuses an existing --directory. See Offline demo.
    autocode verify Check an existing working-tree change, branch or patch against caller-supplied criteria; retain independent review, replay and external-change proof in the canonical evidence format. See Standalone verification.
    autocode chat [BRIEF] [--mode ID] [-- RUN_OPTIONS] Talk to a run in the terminal, the way the VS Code extension does: it prints the run's conversation, asks you only for what the status view leaves to you (an answer, a plan approval, a reply) and runs exactly the command the view names. Plain autocode in an interactive terminal opens it too. With a brief it starts a new run in the project (--in-place, with the start flags of the --mode from autocode modes list, else its default). Without one it picks up the project's open run (or --run-dir RUN), lets you choose when several are open, and asks what you want done when none is. Leaving at a prompt changes nothing. While a stage works, Ctrl-C asks for the view's pause after the current step, a second Ctrl-C interrupts the step and a third stops AutoCode; the chat never exits while AutoCode still runs. A brief that starts with - goes in --brief=TEXT. Where the view names no action it can take, it prints the command to run yourself. Exits 0 when the run completes, 2 when it waits for you. See Terminal chat.
    autocode conversation start\|attach\|read\|send\|refresh\|handoff Core Requirements conversation journal tied to one task run: queue human messages, explicitly refresh its draft and inspect the handoff. See Core Requirements conversations.
    autocode ui Figma design (and optional --build handoff to implementation).
    autocode tasks Run a multi-lane task flow file; accepts --json.
    autocode components Build the components of an architecture record in parallel and combine them (see Task lanes); with --integrate TARGET --run-local, also start the combined system with Docker Compose and run its smoke check (see Running the combined system locally).
    autocode dashboard Local browser dashboard.
    autocode unattended Agent wrapper that refuses operator decisions and reports a stop (see Unattended callers).
    autocode issue brief\|start\|status\|continue\|plan\|pr Read a GitHub issue, work on it through the task-run interface, put the plan waiting for approval in a pull request as a plan file for review (plan), and prepare a pull request (see GitHub issues).
    autocode bridge run\|check\|status The channel bridge daemon: take labeled GitHub issues, start durable runs, relay questions, plan approvals and pauses to the issue, and take an allowlisted actor's reply as the exact action the status view names (see Channel bridge).
    autocode arena init\|ingest\|cases\|run\|report\|propose\|annotate\|compare Run independent benchmark cases, append evidence-backed failure investigations and compare candidate cohorts (see Arena).
    autocode checkpoint --workspace PATH --run-dir RUN --compare CHECKPOINT Compare retained code or restore it by the exact inspected token (--working shows what the Builder has changed so far, display only); accepts --json (see Saved code checkpoints).
    autocode merge [WORKTREE] [--workspace PATH] [--into BRANCH] [--json] Merge a delivered task worktree into its base branch (see Task lanes).
    autocode capture --output FILE -- COMMAND Run a command with exact output retained for retrieval (see Exact output).
    autocode output read\|retrieve Read or retrieve exact retained file bytes (see Exact output).
    autocode visual-capture --config FILE / autocode visual-check --policy FILE Capture visual references or run a source-owned visual check (see Visual checks).
    autocode compare-baseline Compare Vitest failure evidence (see Execution).
    autocode review-pr URL [--post] [--out NEW_DIRECTORY] [--json] -- PROVIDER_OPTIONS / autocode-issue review-pr Fetch the exact PR head into an owned checkout, run Code Reviewer only, and print authenticated findings/evidence. --post submits COMMENT only after every new-side anchor and the head are rechecked (see Pull request reviews).
    autocode review --workspace PATH [--run-dir RUN] Inspect pending human-review criteria and their recorded evidence, then approve, reject with a note, or skip. Reads decisions from terminal or piped input. --show and --json display without prompting; decisions never start a model. See Human review.
    autocode serve start\|stop\|status [--workspace PATH] [--run-dir RUN] Run the run's development server in the foreground from the project's saved serve command (Project settings) on a free loopback port until Ctrl-C or autocode serve stop; stop ends it and waits (--timeout); status shows whether it is configured, running and its address (--json). See Development server.
    autocode forget [--workspace PATH] [--json] Clear only the learned project record; keep explicit configuration, saved runs and evidence. See Project memory.
    autocode clean-worktrees [--yes] [--json] List, then with --yes remove, task worktrees whose runs are complete and whose branch holds their work; records are archived and branches kept (see Task lanes).
    autocode prune-run RUN [--yes] [--json] List, then with --yes delete a run's settled evidence bytes: finished verification-copy trees (tool-containment-*/scratch) and settled job-source stores (<attempt>.source/). Manifests, receipts and hashes are retained, so what was there stays provable; state.json is never modified. Anything still named at file level by state, owned by a live stage or a pending failure recovery, or the newest of its kind is kept with the reason shown.
    autocode bundle RUN [--out FILE] [--with-diff] [--json] Write one redacted archive of a run for a bug report (default WORKSPACE/.autocode/bundles/RUN.tar.gz): the replay recording replay RUN --export writes, so a maintainer can replay it; state.json, activity.jsonl, the stage reports, the check-replay receipts and the last 200 lines of each provider event stream; the resolved settings, doctor --json output and the version. Every file it writes passes the credential redaction exports use, plus the values of secret-named environment variables; a recording that redaction would still change is left out, and the manifest says why. No workspace source unless --with-diff adds the run's diff (against its base commit, else the uncommitted work). manifest.json lists each file's sha256; cite the printed manifest hash in a bug report or a docs/bugs/ note instead of pasting logs. The run directory is only read.
    autocode --version Print the executing package version and its source commit when known. An installed package without a source checkout reports commit unknown; it does not borrow the workspace commit.
    autocode completion bash\|zsh\|fish Print a shell completion script read from the CLI's parsers: the commands, every public option of the main command with its choices, and file names after an option that takes a path. A subcommand completes from the parser it reads: its options, its commands (output read, arena run) and their options, or its argument's choices (completion bash). capture, registry, intervention and dashboard complete only --help. Load it with source <(autocode completion bash) (zsh the same, after compinit; fish autocode completion fish \| source), or save it; see Shell completion.
    autocode models [--provider NAME] [--workspace PATH] [--json] [--prices] [--selection] List the models your plans offer, grouped by plan (subscription or pay per token) and tier (cheap worker, strong judge, Resolver only), and check the route every role of a new run takes. Suggests a replacement for any route you cannot use; exits 1 when one is missing (see Models). A profile default the provider no longer offers is not a gap when automatic selection replaces it with a route it does offer: the verdict then weighs the selected routes and names each replacement, because the profile defaults are only the fallback a run uses when selection cannot field a set (#1995). --prices prints the dated price table instead, and the rate each default route is priced at, or "no rate" (never a zero price); it runs nothing and works offline. --selection reads the tool's own model and login listings (still no model calls) and prints what automatic selection would choose - the route per role with its price and reasoning level, why every other qualified model lost, and which chosen routes the access check would still probe; exits 1 with the account-terms stop when the connected accounts cannot field an independent checker (Choosing models automatically).
    autocode doctor [--workspace PATH] [--engine opencode\|codex\|claude] [--json] Check Python, psutil, Git, each engine (OpenCode must be 1.x; Codex must be logged in), that the workspace is a Git repository with a commit, and the projected run storage (workspace size x its measured ~3x copy growth: worktrees, verification copies, attempt snapshots) against free disk space — a doomed filesystem is a ✖, a tight one a warning with the numbers. Prints the fix for anything missing; exits 1 when not ready. Passes only when the engine a new run uses is ready, resolved as a run resolves it: --engine codex is Codex; without --engine, the engine the project's files set (Project settings) counts as that flag; otherwise (no engine, or --engine opencode) the provider AUTOCODE_PROVIDER or default_provider in ~/.config/autocode/config.toml names, else OpenCode. That provider must answer and list the route each role of a new run takes - its default model, or the route automatic selection replaces that default with (opencode models, as autocode models checks; #1995). AUTOCODE_PROVIDER=codex names a provider config, not the Codex engine. A ready Codex alone does not pass; doctor names --engine codex as the single-login alternative. --engine claude, a project's engine = "claude", or a claude default provider, checks Claude Code instead: claude on PATH and claude auth status --json, run in the agents' environment, reporting a Claude subscription login (engine:claude; an API key, Bedrock or Vertex is refused, by the same check a run makes: the agents' environment and the project's .claude/settings.json), its conformance row, and its routes; a user claude.toml it ignores is a warning. Doctor shows no Claude rows for other runs and never prints the account's email or organization. Lists the settings a new run takes from the project's files (Project settings) and fails on a file a run would refuse. When a new run launches built-in OpenCode stages, names the kernel tool boundary they get on this machine (containment: macOS Seatbelt or Linux bubblewrap and its version, with OpenCode 1.18.33, by the check run setup makes; --json adds it as containment with backend, backend_version and problem, or null for a Codex, Claude Code or configured-provider run), as a warning that does not fail doctor when such a run would be refused without --allow-uncontained-tools (Execution). Runs without psutil and reports it missing. Never reads credentials.
    autocode registry location\|list\|import Registry API (see Registry API).
    autocode runs [--all] [--needs] [--json] Every run of this project (or, with --all, of every registered project) in one read-only table, each JSON row titled with the first line of its task (title): what each run's own status view says it needs, and the command that answers it. Needs-first order, then working, then settled, then runs whose checkpoint cannot be read; the row shows how long since the checkpoint was written. Nothing here starts, resumes or changes a run. Where a saved run's status alone cannot tell an uncertain attempt from one whose retained report only needs repair, the row points at autocode --run-dir RUN --status instead of offering a command that could set accepted work aside. It reads saved checkpoints, so unlike autocode --run-dir RUN --status it inspects no supervised process: a row says what the run last saved, not whether its provider is still alive. registry list is the pointer index with each pointer's availability; runs is what each run now wants from you.
    autocode events [--run-dir RUN] [--follow] One saved run's recorded events as a JSON-lines stream: how it got to where --status says it stands, one event per line, printed exactly as the run wrote it. These are the run's own records — its approvals, answers, contract and configuration changes, routing decisions and self-taken recoveries — not a provider's transcript. --follow keeps printing new events until the run ends the stream, and the status view contract is what ends it: a completed run exits 0, a run that needs a person exits 2 after naming that person's command on stderr, and --timeout SECONDS bounds the wait. Stdout is always JSON lines, so --json does not apply; the envelope is run-event.schema.json, whose kind is an open vocabulary a consumer must tolerate. Read-only, and like runs it inspects no supervised process: a stage hung mid-flight keeps the stream open, so ask autocode --run-dir RUN --status whether it is alive.
    autocode plan --export PATH [--run-dir RUN] [--json] / autocode plan --check PATH [--json] / autocode plan --render PATH [--json] Write a saved run's current plan (shown for approval or approved) as a Markdown file to review in a pull request: a front matter holding the contract body exactly, its goal hash (the SHA-256 of the body) and the revision it came from, then the plan as text generated from it. Never the approval token; credential-shaped text is masked as in bundle, and the export then says the file's goal hash differs from the run's. --check reads such a file and prints its goal hash, and exits 2 when the file cannot be read or its text no longer matches its front matter. --render regenerates that text after the front matter was edited. Reads the checkpoint like events: no run lock, nothing recorded, nothing launched; only the named file is written. --json formats results or error endings as structured JSON. See Reviewing a plan in a pull request.
    autocode wait [--run-dir RUN] [--timeout S] The blocking form of autocode runs: wait on one saved run until it reaches you, ends, or stops advancing on its own. Each second it rereads the checkpoint and, read-only, inspects whether a controller still owns the run — the one question a saved status cannot answer. The outcome names which ended the wait: complete (the run reported TASK_COMPLETE/COMPLETE; exit 0), needs_you (the status view names what you must do, and the command that answers it; exit 2), controller_lost (the saved status is still RUNNING but nothing owns the run, so it will not advance on its own; exit 2, pointing at --status), stopped (anything else; exit 2), or timeout when --timeout SECONDS elapses first (exit 2, reporting the last observed status and controller). --json prints the outcome as exactly one JSON object. Nothing here starts, resumes or changes a run.
    autocode intervention submit\|inspect Queued interventions (see Interventions).

    When working on AutoCode itself, the launcher on PATH may use an older installed package. Run autocode doctor --workspace /path/to/autocode --json to compare its application payload with a verified AutoCode checkout. The install-drift warning names the executing path, the checkout commit and changed, missing or extra package files. Matching payloads do not warn even when an installed build's commit is unknown. Customer repositories are never treated as AutoCode provenance.

    To run the checkout directly from its root, use python tools/autocode.py doctor (or python tools/autocode.py with your ordinary task options). Doctor also prints a deliberately invoked reinstall command for the current interpreter. It never updates an installation or rewrites run state itself.

    The old console-script aliases remain for compatibility. The unit entry points autopilot, autoplanner, autocode-build, autoreview, autoresolver, autocode-orchestrator and autocode-unattended are internal entry points; use autocode and its public subcommands in new instructions. Internal stage and unit names keep their existing meaning.

    Offline demo¶

    Run autocode demo after installation; Git and Python are enough. You do not need OpenCode, Codex or an account. The demo answers its sample requirements question and approves its displayed sample plan, then runs real CLI checks. It first shows a claimed passing check that AutoCode refuses when its independent rerun fails. The successful sample also stops at the completion gate until demo acceptance of the artifact is recorded. These automatic approvals apply only to the new demo project.

    The command prints the run directory, canonical evidence record and demo.json, and keeps every output inside its new directory. To choose where it goes, use autocode demo --directory /path/to/new-demo; the directory must not exist. Remove that directory after inspection. Fake-provider evidence demonstrates the workflow and is separate from the real-model reliability results.

    Common flags¶

    Supplying a brief¶

    Flag Meaning
    --brief TEXT Start a new run with literal task text; --brief - reads UTF-8 bytes from stdin. Mutually exclusive with a positional task, --brief-file, saved-run options and resume.
    --brief-file PATH Start a new run with the file's exact UTF-8 task text, retaining line breaks and trailing whitespace. Mutually exclusive with a positional task, --brief, saved-run options and resume.

    Use autocode --brief-file brief.txt or pipe UTF-8 text into autocode --brief - to preserve backticks, $(), quotes and line breaks exactly. These inputs start a new run and cannot accompany a positional task, resume or --run-dir. An empty or invalid UTF-8 input is refused before creating a run.

    --brief TEXT and the positional task remain available. The shell processes arguments before AutoCode receives them: use single quotes around literal shell syntax, for example autocode 'Fix the `run()` function', or use a file or stdin when the brief contains embedded single quotes. AutoCode cannot recover text already changed by the caller's shell. The saved task and its UTF-8 SHA-256 appear as view.task and view.task_sha256 in status JSON; compare them with the source brief before continuing.

    Targeting a run¶

    Flag Meaning
    --workspace /path Committed Git workspace to work in. Defaults to the current directory. Without a task or --run-dir, where AutoCode looks for the run to act on.
    --run-dir /path Act on this saved run, from any directory. Without --workspace, the run's own checkout is used.
    --in-place Start a new task in the selected checkout instead of a fresh worktree. Uncommitted and untracked files there count as the code the task starts from (see Workflow). Only one run's agents work in a checkout at a time; a second run exits with status 2 and changes nothing (see Task lanes).
    --workflow build\|bugfix\|review\|design\|discuss Name the kind of job instead of having Requirements (or, on a flow without it, the recognizer) name it from the request. A pinned build still runs Requirements first; any other kind starts its own first stage. Also accepted by a saved run whose job is not named yet. A run whose job is already decided keeps it: start a new run to change it (see Workflow).
    --status Read-only status, including milestone_checkpoint, interventions, active_stage.activity.
    --json Stdout carries exactly one JSON object unless the invocation ends with an error message other than a refused setting (below); everything else the invocation prints goes to stderr. A finished or paused run prints the same payload --status prints. A user action (an approval, answer, feedback, resolver response and the like) prints that payload plus result: exit_code, saved, message (the text a person would have read) and error, which is {"code": "input_rejected", "message": …} when the input was refused and null otherwise. A refusal before the run loads prints {"result": …} alone. Any other invocation that loaded the run and returned without printing the payload, such as one stopped by --pause-after-stage or a time or iteration limit, prints the saved run's payload plus result. A setting the run's configuration refuses as the run loads still ends with autocode: … on stderr, and also prints the saved run's payload plus result ({"result": …} alone for a new run refused before its first checkpoint), whose error is input_rejected with the refusal text. Such settings include --single-model, --spec-first, --blind-tests, --utility-model, --builder-strong-model or a different --engine on a saved run, --single-model with a per-role model flag, --max-milestone-seconds on a saved run without milestone checkpoints, and the tool-containment refusals: --allow-uncontained-tools on a run with no built-in OpenCode stage, or a built-in OpenCode run without it where the kernel tool boundary is unavailable. The refused setting is not saved, though a new run without --in-place may already have created its task worktree and branch, which result.message names. In a native visual run (a task with a VISUAL_REVIEW_PROFILE= directive) such a refusal is instead saved as a PAUSED_INVALID_OUTPUT pause and printed like any other pause, with error null. Any other invocation that ends with an error message (autocode: … or argparse's usage: text on stderr) prints nothing on stdout. A refusal reported in result also prints {"error": …} on its own line of stderr: its last line, except after a refused setting, where autocode: … follows. status-view.schema.json describes the status payload. The lone {"result": …} does not validate against the schema's root; its result validates against the schema's properties.result. Exit codes are unchanged (Exit codes); a usage error still prints argparse's text. The read-only commands (--status, --explain, --dry-run, doctor --json, registry, usage --json) print their own output and are unaffected.
    --explain Read-only explanation of a saved run's stop and what the next command does. With an explicit task in a Git workspace, previews the initial explanation without creating a run. An explicit --run-dir cannot accompany a new task or new-run inputs.
    --dry-run Read-only preview; never emits an accepted handoff.
    --inspect-evidence With --status, inspect the current source and saved verification evidence without running checks.

    Understanding a stop¶

    The status view adds pause_category, its readable pause_category_label, and next_command. The category says whose action is needed; the exact status and stop_reason remain available as detail, together with the existing needs and recovery tokens.

    Category Meaning
    your_decision — Your decision Inspect and answer a question, approve a plan, or authorize a recovery or limit change.
    your_environment — Your environment Repair the workspace, configuration, prerequisites or other local setup.
    model_or_provider — Model or provider Inspect a model refusal, quota stop, provider failure or incomplete model output.
    autocode — AutoCode Inspect an internal consistency, supervision or completion-proof stop.

    Rejected human actions and invalid configuration changes also print the current recovery summary and command. Answer a clarification with --answer Q=TEXT and the displayed private resolver token; --resolver-response is for an operational request. A rejected response does not turn a clarification into an operational pause or grant a retry.

    Use the offered next_command under the category. It is derived from the same current needs and actions as the existing recovery instructions; the category never approves, retries or changes a limit. next_command is null when the run has no executable next action. Resolve any stated prerequisite before running a command that resumes work. Replace ANSWER, MODEL, N or GOAL_FILE with your intended input; a displayed token uses its paired environment variable with the - selector. When recovery has two steps, next_command gives the first one; inspect status again after it. A missing issued token offers a noninteractive display, and a missing source identity offers inspection rather than an unbound retry. autocode explain describes the stop and the offered action. See the status view contract.

    Which run a command acts on¶

    A command with no task and no --run-dir acts on a saved run found from the --workspace directory: the run directory you are in; otherwise the runs of the task worktree you are in; otherwise the project's in-place runs and the runs of all its task worktrees. It names the run on stderr (Using the saved run RUN (STATUS, ...)) and goes on as if you had passed --run-dir RUN.

    Command Run it takes
    autocode, autocode resume, --resume-paused and its --retry-* companions, --unit The only unfinished run. A finished run (TASK_COMPLETE, or stopped) is never relaunched this way, and a run that autocode tasks drives is left to that command.
    --status, --explain, --dry-run, autocode status, autocode explain The only unfinished run; with none, the latest finished one.
    --show-goal, --answer, --approve-goal, --feedback and the other user actions The only unfinished run, preferring one no task flow drives. These save the run, so they never pick a finished one.
    --follow-up The most recently completed run, preferring one no task flow drives. Refused when a run started after it finished has not finished: name the run with --run-dir.

    Keeping authorization tokens out of argv¶

    These options accept - to read their paired environment variable:

    Token option Environment variable
    --resolver-token AUTOCODE_RESOLVER_TOKEN
    --job-retry-token AUTOCODE_JOB_RETRY_TOKEN
    --recover-job-report AUTOCODE_RECOVER_JOB_REPORT
    --approve-goal AUTOCODE_APPROVE_GOAL_TOKEN
    --review-token AUTOCODE_REVIEW_TOKEN
    --expected-goal-token AUTOCODE_EXPECTED_GOAL_TOKEN
    --expected-recovery-token AUTOCODE_EXPECTED_RECOVERY_TOKEN
    checkpoint --expected-token AUTOCODE_CHECKPOINT_EXPECTED_TOKEN

    Prefer this on shared machines: Linux exposes /proc/<pid>/cmdline to every local user, while /proc/<pid>/environ is readable only by the owner, and a typed token also lands in shell history. The environment variable alone never authorizes anything — the flag must still be present. TaskRun, dashboard actions and the trial driver pass these tokens through each CLI child's environment. Their process arguments and saved command records contain -. Literal CLI tokens remain supported. The controller always removes all eight variables before launching a provider or test command, even if named in AUTOCODE_PASS_ENV. Programmatic command builders require full token option names; abbreviated token options are refused before recording or launch.

    With several unfinished runs the command changes nothing, exits 2 and lists them with the --run-dir command for each. With no run it says where it looked; with only finished runs, a bare autocode names the latest one instead of relaunching it. Inside a run directory whose state.json is missing or cannot be used, or one autocode clean-worktrees archived, it refuses rather than pick another run. A task, or a new-run option (--in-place, --figma-file, --figma-manifest, --figma-review, --ui-run, --builder-strong-model, --conversation-handoff, --test-root, --package), starts a new run instead; autocode resume never does.

    Conversation and approval¶

    --status keeps its JSON document on stdout and prints a short pending-question list and the current Resolver token on stderr. After a successful --answer, stderr shows the questions still open and their new token, or says there are no questions left to answer. Use that new token for the next answer; answering does not approve a plan or start a model.

    Flag Meaning
    --chat Interactive chat mode (default in a terminal).
    --no-chat One command per turn (default for non-interactive).
    --answer 'Q1=…' Answer a question the run is waiting on (repeatable; the status view's needs.kind is answer). Requires the current --resolver-token shown by Resolver. A finished run waits on none: the questions in its report take --follow-up (see Waiting or finished).

    Waiting or finished¶

    --follow-up continues only a finished run (TASK_COMPLETE). A waiting, paused or blocked run refuses it (exit 2, state unchanged): answer it (--answer/--delegate with --resolver-token), approve or correct it (--approve-goal/--feedback), or resume it. Jobs that report without waiting for a reply (design review, discussion, code review) complete with their questions or findings in their report; you reply to them with --follow-up. After a design turn, "Build it." builds that design as approved (checked against the code first, no requirements gathering or questions, plan approval still required). The build gets a plan of its own: the design turn's plan (which wrote no code), with whatever earlier turns agreed that it carried, and its open non-blocking findings are archived in the run, not revised; the design is now the requirements. After a design review instead, building the design it approved revises the plan in force. A follow-up builds as approved only the design its previous turn wrote, or the design a design review approved; any other document is planned from requirements as usual.

    waiting for you needs.kind is answer, approve_plan, review or planning_budget --answer/--delegate with --resolver-token, --approve-goal, --approve-review, --feedback answer, approve_plan, approve_review, feedback

    The wrong one is refused with exit 2 and the run left as it was. --follow-up on an unfinished run lists the alternatives (answer, approve or correct, resume). On a finished run, --answer, --delegate or --delegate-all says: "This run is finished and waits for no answer; reply to the questions in its report with --follow-up TEXT", and --feedback, --edit-goal, --goal-file or --reject-assumption says it would reopen the run without a new turn. Without --run-dir, --follow-up is also refused when a run started after the latest finished one has not finished: the message lists that run, and the command that continues the finished one anyway. Through TaskRun these raise TaskRunError.

    Replying to a design review¶

    A design review never waits for its questions: the run completes with them in review/design-review.json, and you answer with --follow-up ("Ordering is per-domain."). The Architect is asked to keep a concern that is a problem only under one answer to its question advisory until you answer. A reply recognized as design makes the Architect revise the same review instead of writing a new one. It is asked to:

    • keep every earlier concern under its id, open or resolved, and to drop or renumber none;
    • keep a concern the reply settles with status resolved and a resolution saying what settled it (an answer can also make a concern blocking), and to add a concern only for a problem the reply exposes;
    • drop the questions the reply answered and keep the others under their ids.

    The runner refuses a revision that leaves out an earlier concern id, uses an id twice, resolves a concern without a resolution or resolves one raised in that revision, or whose verdict is not request_changes exactly when an open concern is blocking. A reply that names a different design gets a fresh review (revision 1); a reply asking for a new design hands it to the build pipeline, as a first request would.

    revision is the review's number, and revisions keeps one entry per review: the message that prompted it (said, null for the run's first review), its feedback receipt (event_id), the verdict, and the ids of its open blocking, open advisory and resolved concerns and of its questions. The report you reply to must be the one the Architect wrote: if review/design-review.json was edited since, --follow-up exits 2 with "changed since the Architect's review; restore it or start a new run".

    Execution and recovery¶

    autocode resume can replace --resume-paused alongside a recovery companion such as --grant-recovery N, --retry-failed-stage, or an explicit budget change. This also works when AutoResolver has published the operational pause as WAITING_FOR_USER, provided its saved request is still valid. Bare resume does not acknowledge that published request; ordinary questions and approvals still require their own actions. Recovery eligibility and token checks are unchanged.

    Project settings¶

    A team keeps the settings it would otherwise type on every new run in .autocode/config.toml in the workspace, or, in a Python project, under [tool.autocode] in pyproject.toml (config.toml wins a key both set). Commit the file like any other: the .autocode/.gitignore AutoCode creates leaves config.toml trackable. In a checkout whose .autocode/.gitignore AutoCode created before this, add the line !/config.toml to it, or git add -f .autocode/config.toml.

    engine = "opencode"
test-command = "python -m pytest -q"
sol-model = "openai/gpt-6-sol"
terra-reasoning-effort = "high"
max-seconds = 7200

    require-approver has no flag: one plain Git email address, or a list of them, allowed to approve the run's plan and reviews and to accept its completion, such as require-approver = ["lead@example.com", "deputy@example.com"]. A run started with it refuses a plan approval, an artifact acceptance or --accept-completion when git -C WORKSPACE config --get user.email, for the run's saved workspace in AutoCode's own environment, is not listed (compared without regard to case), before anything is approved, and stays at the same stop; an --as name never counts. Without it anyone may approve. No flag sets or overrides it. It guards against an approval under the wrong configured Git identity, not against someone who deliberately sets a listed address (Git's environment variables or a repository-local user.email change what is checked): it is not authentication. A replay never takes it, and autocode components child runs read it from their own worktree, so only a committed file reaches them (Required approver).

    serve has no flag either: the command that runs the project's development server, with {port} where the port goes. It is a string, or in .autocode/config.toml a table that also names the path that answers once the server is ready (ready-path, any answer below 400) and how long to wait for it (ready-seconds, 1 to 600, default 60); pyproject.toml takes only the string. A new run saves it with its settings, so an edit to the file, including one the Builder makes, never changes the command a run serves with. Every {port} is replaced with a free loopback port; any other text goes to the shell unchanged.

    sensitive-paths has no flag either: a list of shell-style path patterns over repository-relative paths (src/billing/**, *.lock, migrations/) naming the files a shorter planning path may never touch, saved with a new run. The compact bug-fix planning path (--compact-bugfix-planning) takes the full path for a fix whose files match any pattern, and for a project that declares no list at all; an empty list (sensitive-paths = []) declares that nothing is sensitive. Matching is by path only, so it cannot see sensitive behaviour in ordinary files; that is why the compact path also stays off unless a person opts the run into it (Compact planning for bug fixes).

    [serve]
command = "npm run dev -- --host 127.0.0.1 --port {port}"
ready-path = "/"
ready-seconds = 90

    A flag on the command line wins over the file, and over any file key it cannot be combined with: a typed --single-model drops the file's role models, a typed role model drops its single-model, and a typed iteration ceiling drops its max-iterations and unlimited-iterations. The file wins over the built-in default; no environment variable sets these keys. A setting from the file counts as typed, so a budget the team set is never extended as a runner default. A new run prints which settings it took from which file. Only a new run reads the file, including one started from a design handoff with --ui-run and no typed task: a saved run keeps the settings it started with, so changing the file never alters a run in progress.

    engine = "claude" is allowed: it selects the built-in Claude Code provider, which runs AutoCode's fixed command line, as engine = "codex" does. A project cannot choose the provider (provider, or a role's astra-provider, terra-provider, sol-provider, completion-provider): it runs a command you installed, so it comes from --provider, AUTOCODE_PROVIDER or default_provider in ~/.config/autocode/config.toml. Nor task-preflight, the operator's prerequisite manifest. A file that names either, an unknown key, or a value its flag would refuse stops a new run before it starts, naming the file and the key. autocode doctor lists each setting a new run would take and the file it came from, and fails on such a file.

    Development server¶

    autocode serve start runs the project's serve command for a saved run and keeps it in the foreground. AutoCode picks a free port on 127.0.0.1, puts it wherever the command says {port} and in PORT, sets HOST=127.0.0.1, and runs the command in the run's workspace with credentials removed from its environment, under the same process supervision as a test command. Once the server answers (any connection, or a status below 400 at ready-path) it prints Serving http://127.0.0.1:PORT/. Ctrl-C, closing the terminal or autocode serve stop from another terminal stops its whole process group; if the autocode serve start process dies, its supervisor ends the server. A run has at most one server; a second start is refused while one runs.

    start follows the run's code. After each code-changing step the run applies (each new code checkpoint), it stops the server and starts it again, on the same port when that port can be bound again, so the address stays the same, and prints Serving http://127.0.0.1:PORT/ again after a code change. It reads the run's state.json for this and never writes it. A pause or the run's completion leaves the server running, so you can try the app while you answer a question, approve a plan or review the result; it stops only when you stop it.

    The server never starts, pauses or decides a stage. Its record is dev-server.json in the run directory, and each start keeps its output and supervision receipt under dev-server/. autocode serve status and autocode --status (view.dev_server) show configured, status (off, starting, running, stopped, exited, failed, or lost when the process that served it is gone), the url while it runs, the command, its port, times, exit_code, reason, log, restarts (how many code changes restarted it), code_checkpoint (the code checkpoint it serves) and waiting. A server that exits, or does not answer within ready-seconds, is recorded as exited or failed with its last output, which start prints; start then keeps waiting (waiting is true) and starts it again after the run's next code change, so a step that fixes a broken app brings the preview back. autocode serve stop or Ctrl-C ends the wait. Once the run has completed no step will change its code, so such a server ends start with exit status 1 instead. A run started before its project named serve has none: name it in .autocode/config.toml and start a new run.

    Terminal chat¶

    autocode chat --execution durable_local "YOUR TASK" opts a new run into the durable local worker mode on a supported persistent Linux host. The core checks an existing systemd user manager (254+) and existing linger policy; it never configures them. Normal quit, Ctrl-D, terminal closure and SSH disconnect leave that worker running. Reopen with autocode chat --run-dir RUN. Repeated Ctrl-C requests only the current boundary pause, without escalating to worker termination. This does not change ordinary owned-worker behavior or migrate saved runs. While the current view advertises durable detach support, /open, /new, /tab and the tab keys are available during work. The worker being left continues independently. Returning to an idle boundary reads status and waits for explicit Continue.

    Within this terminal session, each of the most recent 32 run identities keeps its transcript, unsent draft and cursor, scroll, log filter and panel choices. Titles are display text; workspace and run paths select the context. Switching always reads fresh core status before a decision. A changed question or plan keeps its earlier draft in input history for explicit recovery with Up, rather than filling the new question automatically. Pending restore confirmations and queued keys never transfer between runs. If a target disappears or cannot be read, Enter retries its status and /runs, /open or /tab selects another; typed text cannot submit a task decision while status is unavailable.

    /new opens a local request composer; no core run or tab is created until a brief is submitted. An empty request returns to the original context. Unsent drafts and view choices live only in this TUI process. After restart, saved core conversations, registered runs and existing project input history remain; session drafts, scroll and filters do not.

    autocode chat is the terminal client of the task-run interface, beside the VS Code extension and the browser dashboard. It reads only autocode --status, autocode runs --json and runs --all --json (your chats, in this project and every registered one) and autocode modes list --json (a new run's mode), shows the conversation the view carries (view.chat), and acts only through the view's named actions: next_command, the chat.input message offer and the pause offer. The rules it reads them by are in tools/autocode_client_actions.py, the same ones the extension (vscode-extension/src/core/next-command.ts) and the headless conformance client follow, so a person gets the same choices in each:

    • Requirements asks in its own words; you reply in yours, and confirm the understanding it summarizes with y. Before the plan is prepared the chat shows the core's spend confirmation (review.spend_confirmation: what planning spends) and asks Prepare plan? [y/N]; anything but yes sends nothing. A mode that could plan at once (spend_confirmation start; the core lists none since quick was removed on 2026-10-22) would ask Start it? [y/N] before the run starts instead, as the VS Code extension does.
    • A question with options takes the option's number or your own answer; Enter takes the proposed default when there is one.
    • The plan is shown from displayed_plan and approved with y only while its token is still the one shown; anything else you type is sent as plan feedback.
    • A stop only you decide (a pause, a stopped job) says why and continues only on your y; a Resolver request takes your reply.
    • When the run completes you can type a follow-up, or press Enter to finish.
    autocode                            # in a terminal: pick up the open run, or ask what to do
autocode chat "Add a --verbose flag to greet.py"
autocode chat                       # the same as plain autocode in a terminal
autocode chat --mode full "Fix the README typo" -- --engine claude
autocode chat --line                # the line-by-line prompts, even in a terminal

    In a terminal the chat takes the whole screen: a wordmark splash, the conversation in a scrollable transcript with a colored label for each speaker (PgUp/PgDn), the current question or activity above a boxed composer, and a hint bar. The composer is labeled New chat when typing there starts a run and Reply when it answers the run (Up/Down for history, Ctrl-W/Ctrl-U to edit, Enter to send, Ctrl-D to leave). A paste stays in the composer as one reply, line breaks included, until you press Enter. A plan, a question or a stop is shown where it is asked, and Ctrl-C keeps its meaning: the first asks the run to pause after the current step, the second interrupts it. When the chat ends, its last words stay on the terminal: an error, where to pick the run up, or the command a stop leaves for you to run. --line keeps the plain prompts, and scripts get them automatically when there is no terminal.

    In a terminal at least 100 columns wide, a side panel shows the run beside the conversation once it has a plan: where it is and what it needs from you, the current step and its last few attempts (the view's chat.progress), what the running step is doing (the commands it runs, the files it edits and the tools it calls, from the view's chat.activity), each requirement and task with its state, open problems, and a log of how the run moved (a stage starting or finishing, an attempt finishing, a command run, a file edited, a task done, a requirement checked). The status row under the conversation names the newest command or edit, in any width. A command that exited 0 is shown as run, not as passing: only the requirement checks say what passed. Everything in it comes from the status views the chat already reads.

    While AutoCode works, a live log under the conversation shows what each running agent is thinking and doing as it happens: its reasoning (∴), its messages (»), the commands it runs ($), the files it edits (±) and the other tools it calls, each line led by the agent's name (Builder · task M2, Plan Reviewer). Parallel Builders each appear under their own name. It comes from the view's chat.log, is refreshed with each status read (every two seconds) and keeps the last 500 entries; the composer stays below it, so you can keep typing commands. It shows on its own in a terminal at least 24 rows tall once an agent is working. Reasoning is shown on one line with its newest words, and tool output is never shown. Like the activity rows it is display only: a thought is not a report and a command shown is not a passed check.

    /diff List the saved code steps with the files each changed; /diff N shows the files and the diff changed since step N

    /runs Your chats in every project, open and finished, grouped by project: this project first, then the others by their latest activity, newest chat first in each. Each shows its request, its state and when it last moved; a chat whose run was removed is left out and counted. Also at the first "What do you want done?"

Only an action the connection offers is run
    /panel Show or hide the side panel
    /live [NAME\|thinking\|messages\|tools\|all\|off] Show or hide the live agent log. With a word it keeps only one agent (any part of its name, such as M2 or reviewer) or one kind of entry; all shows everything again and off hides it. Where the terminal is too short for it, the newest entries are printed in the conversation
    /attention or F8 Inspect current saved questions, decisions and completed turns across registered projects, even before selecting a chat. a acknowledges the selected alert, Enter opens its chat, r requests a refreshed snapshot and Esc returns to the original draft and cursor. Acknowledgement leaves the task's answer or plan approval pending. Unavailable inventory and unknown read state remain visible.

    /help List the commands
    /quit At a question: leave the chat; the run stays as it is

    The side panel's Usage section shows the accounted subtotal, missing prices or usage, active/pending attempts and any configured accounting cap. /details separates provider-reported figures, dated-table estimates and historical comparison estimates; subscription/API-equivalent estimates are not the subscription invoice. Cache and reasoning counts are shown as subsets of input and output, never added twice. Historical attempt models and efforts come from their launch records, while saved routes describe future attempts. Missing fields in older cores remain unknown. Displaying this information calls no model and changes no route, cap or workflow.

    The header keeps a last-read status visible while you read history; new background messages do not move the history viewport. If the current tab's read fails, the header says the previous read is being shown. It separates the viewer's successful read age (local monotonic time) from the core snapshot's sample time. /details shows the full sample timestamp and opaque checkpoint/workspace/run identity. Missing or mismatched optional metadata stays unknown. A new poll can refresh the local receipt while the core checkpoint stays identical; neither timestamp is a worker-liveness check, evidence acceptance or meaningful work progress. Failed reads retain the last snapshot under a last-known label; a fresh read clears that read error. No ETA or completion percentage is inferred.

    A Plan path section appears for a bug-fix run that recorded which planning path it took (the status view's stage_policy, compact planning): compact: Planner draft omitted with what covers the omission (the runner's draft, the Plan Reviewer, your approval, the regression proof), or full: every planning stage runs with the first reason the full path was kept, and where a review fell back to it. /details lists every reason, the decision rows and the hashes the decision rests on. It renders the core's record and offers no action.

    The Verification section and /details distinguish the core's current delivery gate from report inspection. A recorded PASS can be unchecked or stale, and a verified delivery can still have a report not explicitly inspected by that status request. Criteria show their recorded results, supplied coverage state, pending human acceptance and evidence references. Retained edits and successful commands alone do not establish accepted evidence. Recovery details show the core's reason, retained work and offered actions; /diff remains the way to inspect saved changes. Recorded execution, observed interval wall time, current-attempt duration and answered-request waiting are shown only where the core supplies those measurements; missing durations stay unknown, and overlapping categories are not added together.

    A command never answers the question that is waiting. To send a reply that starts with /, type //. /diff and /undo take only the compare and restore actions the status view names for a saved step (Saved code checkpoints); the view offers going back only at a pause it can restore from, and /undo says why when it cannot.

    The first screen says what a new chat starts with (New chats: Full · OpenCode). A choice made with /mode, /engine or /connect … use is kept for the project in .autocode/chat-settings.json; options after -- on the command line take its place for that chat. While Requirements writes its reply, the reply grows on screen as it is written (the view's streaming message). The terminal rings its bell when AutoCode has worked and now needs you, and a chat you opened earlier in the session is checked while AutoCode works: when it starts to wait for you or finishes, the chat says so.

    autocode in a project with earlier chats says how many there are.     Unattended callers (agents)¶

    autocode unattended (or the internal compatibility wrapper autocode-unattended / scripts/autocode-unattended from a checkout) runs AutoCode for another agent without letting that agent make the operator's decisions. It takes AutoCode's own arguments but refuses every decision or recovery flag (--answer, --delegate*, --approve-*, --resume-paused, --retry-*, --feedback, --follow-up, --accept-completion, --close-finding, --close-reason, --resolver-response, …, including abbreviations) and every flag that sets operator policy instead of a person: --skip-requirements (answers Requirements questions by default), --skip-to-build (approves the plan), --allow-uncontained-tools (lifts the tool boundary) and --accept-source-edit. Setup, routing and start-time budgets (--max-seconds, --unlimited-iterations, model flags) stay allowed. The two classes are DECISION_FLAGS and START_FLAGS in tools/autocode_decision_flags.py; a test fails when a parser flag is in neither, the command word resume (on a paused or blocked run it stands for --resume-paused; a bare relaunch still continues a run that is not paused) and the intervention, tasks, ui, registry, capture and compare-baseline subcommands. It forces --no-chat with no stdin, and when AutoCode stops it prints --status and tells the caller to report and stop. Exit codes are AutoCode's.

    When a run completes, the wrapper prints the command to analyze it: autocode unattended --analyze --run-dir RUN [--out DIR]. That launches no stage; it reads the saved run and reports the outcome, each acceptance criterion with its recorded status and evidence, findings, stages (role, time, exit, tokens, report path), cost by role (model calls, seconds and tokens per role, with report-format repair calls counted separately), and the code changes against the task's base commit, including new untracked files, plus a summary of the run's always-on activity log. --out saves analysis.md, the full changes.diff and a copy of activity.jsonl.

    To lock a Claude Code agent to it, launch the agent from a copy of examples/agent-operator: its .claude/settings.json allows only autocode-unattended and read-only tools, denies edits and other AutoCode or provider commands, and uses dontAsk so anything else is refused without a prompt. Its CLAUDE.md has the agent report stops verbatim and, after completion, analyze the work read-only. Keep that directory outside the target workspace.

    Exit codes¶

    Code Outcome When What --json prints
    0 completed The task completed: view.done is true. The status payload; with result when the invocation also acted.
    0 saved A user action (an approval, answer, review decision, feedback and the like) was saved. The status payload plus result, whose saved is true.
    0 read A read printed what it read: --status, runs, or events without --follow. That output; --status prints the status payload.
    2 stopped The run stopped short of completing: it waits on a person (a question, an approval, a review, a requested pause) or on its environment, a provider or AutoCode. view.pause_category says whose action it needs and view.next_command what answers it. wait also exits 2 for a stopped run, and for endings that are not stops (below). The status payload; with result unless the run printed the payload itself as it stopped. wait --json prints its own outcome object instead (below).
    2 refused The input was refused and not saved. A new run refused for a setting may already have created its task worktree and branch (without --in-place). For a refused action on the loaded run, or a setting the run's configuration refuses (such as --single-model or --spec-first on a saved run, or --allow-uncontained-tools where it does not apply; the --json option above lists more), the status payload plus result, whose error.code is input_rejected; for a refusal before the run loads, or a setting refused before a new run's first checkpoint, that result alone. A refused setting still ends stderr with autocode: …. A native visual run saves a refused setting as a PAUSED_INVALID_OUTPUT pause instead (stopped, error null).
    2 usage The arguments did not parse, or a later check of them ended with argparse's error. Nothing on stdout: argparse's usage text on stderr.

    autocode wait only watches a run, and its outcome says why the wait ended. It exits 0 for complete. It exits 2 for needs_you (the run waits on you) and stopped (the run stopped otherwise), and also for three endings that are not stops of the run: controller_lost (the saved status says RUNNING but nothing owns the run), timeout (--timeout elapsed first) and unreadable (the checkpoint could not be read). It also exits 2 when it cannot tell which run to wait on (none is saved, or several are and no --run-dir names one), with autocode wait: … on stderr and nothing on stdout. Otherwise wait --json prints that outcome object (outcome, status, reason and, when it has one, next_command), never the status payload.

    tests/test_json_contract.py holds the CLI to this table on a fake run that stops only to wait on you (view.pause_category is your_decision): at a requested pause (--pause-after-stage), a question, the plan approval and a human review, then it completes. At each stop the test runs --status, a plain relaunch, the command view.next_command offers (resume, answer, approve the plan, approve the review), that command with stale tokens, wait --json, runs --json, events and a usage error. It validates each status payload the main command prints under --json or --status against status-view.schema.json, and the lone {"result": …} against its properties.result. It validates each events line against run-event.schema.json, and checks that wait --json and runs --json, which print their own shapes, report the same status and next_command as the status view. The fake run never stops for its environment, a provider or AutoCode. tests/test_json_output.py covers those: the iteration and time limits (AutoCode), and a saved auth or rate-limit pause (your_environment / model_or_provider) under --status and --json.

    Because 2 has several meanings, scripts should prefer --json: view.done, view.needs and view.pause_category say which outcome it was, and after an action result.saved and result.error.code say whether it was saved or refused. The exit codes stay 0 and 2 for compatibility.

    Exact tool output¶

    Use --tool-output-mode raw|conservative for AutoCode capture/file-read display. autocode output read FILE returns exact sections with retained originals; autocode output retrieve SHA256 --raw recovers exact bytes. See exact output transport for options, recovery and measurement limits. Native provider tools keep their existing behavior.

    A failed read-only workflow job exposes an exact retry_job action in status. After inspecting the archived attempt, retry with --resume-paused --retry-failed-stage --job-retry-token TOKEN using its current needs.job_retry_token. Plain resume does not repeat the job. Unrestored source blocks retry until the exact original source is restored. The CLI verifies file bytes, modes and Git HEAD even when a capture artifact is missing; changed model/limits still invalidate the retry. An older attempt with no saved original identity exposes recover_source and an explanation instead of a retry action. Inspect its archive and current changes before starting a new run.

    A failed Builder classification can also offer retry_job for the Investigator at PAUSED_BUILDER_CLASSIFICATION. Inspect needs.retained_evidence and use the current needs.job_retry_token through AUTOCODE_JOB_RETRY_TOKEN with --resume-paused --retry-failed-stage --job-retry-token -. Run this retry separately from feedback, approval, source acceptance or abandonment. It starts one fresh read-only investigation of the same task, contract, source and failure; any queued Resolver proposal stays unassigned until the normal classification policy accepts the new diagnosis. Previous failures, repair counts, approvals, Builder allowances and time limits remain in force. Status offers --edit-goal FILE and requires fresh approval when a remaining failure or classification limit prevents retry. Older checkpoints that discarded the failed request also require a plan correction or a new run; plain resume cannot reconstruct the missing proposal.

    A job its provider's content filter refused (PAUSED_CONTENT_FILTER) or that ran out of quota (PAUSED_BUDGET) pauses the same way, and its stop names the cause and the model. The same model is likely to refuse again, so needs.route carries the job's model question. --job-retry-token is accepted without --resume-paused --retry-failed-stage only together with that answer: --answer route-ROLE=MODEL --job-retry-token TOKEN checks the model the way a launch would, records a route_assignment and issues a new token for the new model. The old token stops working, and the exact retry with the new token is the only way on: --resume-paused --retry-failed-stage --job-retry-token NEW_TOKEN. After a refusal, until a model is named, the status view's needs.action is that answer and the recovery card offers no retry, since the exact retry would replay the refused model. The Architect, Analyst and Investigator have no --ROLE-model flag, so this answer is how they move. The answer changes only that model: given with a limit or another role's model, with or without its token, it is refused and nothing is saved. It issues a new token, so it is given on its own: next to --resume-paused --retry-failed-stage it is refused before anything is read or saved. At that stop --abandon-stage is refused, and a --ROLE-model flag for the stopped role is refused with this advice instead of being saved (saving it would make the retry stale); only a flag that puts back the model the retry is bound to is saved. The same flag is refused while the job's attempt is still uncertain, including with --abandon-stage in the same command: run --abandon-stage ATTEMPT alone, then answer with the token it shows. After a quota stop, the unchanged retry with the shown token also works once the quota resets. A stopped stuck-stage Investigator (investigate_stuck) accepts route-stuck_investigator: its answer saves both the preparation pin and the current route, then issues a new exact-retry token. Use that token for the retry. Changing --investigator-model alone at this stop is refused before saving settings. An older Investigator stop can expose the same question only when its retained attempt, launch configuration and original source establish that model. Other older job stops without a saved model question keep their exact retry.

    Standalone verification¶

    autocode verify accepts --workspace, --base, either --branch or --patch, and either --criteria or --criteria-file. Criteria are explicit JSON; they are never inferred. --out names a fresh output directory. --record reads an existing verification and checks freshness instead of running models or checks. Review controls are --engine, --provider, --model, --reasoning-effort, --evidence-provenance, --max-seconds and --max-stage-seconds. --suite-command selects the proof suite and --check-timeout bounds each runner command. --json emits the verdict and evidence metadata. See Standalone verification for the criteria format, proof modes and exit codes.

    autocode modes list lists the run modes a client may offer for a new run (--json for the version-1 list). See Run modes for clients.

    autocode connections list|check|login|setup manages backend setup; list and check return status without inference, and login delegates to the backend in a terminal. connections setup ends by naming the route each role will use, and connections list --routes --json returns the same choice as routes[] — both read the connected tool's own model listing and launch no model. See Connections for clients.
