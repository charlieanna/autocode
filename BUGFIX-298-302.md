ISSUE #298 — Idle watchdog (300s) kills long-thinking builders (MiMo)

Problem: limits.idle_timeout_seconds defaults to 300 (tools/autocode_configure.py, tools/autocode_goal_lifecycle.py). ActivityMonitor (tools/autocode_activity.py) treats "no tool events" as idle even while the provider is still streaming. MiMo Builder stalls with idle=299s, changed_files=[], archived non-terminal.

Required behavior:
1. Treat increasing provider token counts / stream activity as progress, not only tool completions (see tools/autocode_activity.py activity snapshots used by tools/autocode.py run_role).
2. When the configured model is MiMo family (xiaomi-token-plan-sgp/* or mimo-*), use a default idle timeout of at least 900 seconds unless the user explicitly set --max-idle-seconds.
3. Stall messages must include the numeric limit and how to change it.

Tests: unit tests for activity idle classification (tool-less streaming is not idle); configure default idle for mimo routes.

ISSUE #299 — Regression proof cannot fail-on-base when tests observe a symbol the fix introduces

Problem: tools/autocode_verify.py _judge_regression (new_behavior=False for bugfix) requires ran_and_failed & passed. If tests only fail to collect on base because they reference a symbol the fix adds, fail_to_pass is empty and the message is generic. base_patch exists but only via tools/autocode_regression.py reviewed_patch() from review follow-up (change_patch), not operator CLI.

Required behavior:
1. If base run has collection_errors whose undefined identifiers are symbols added by the candidate sources, record a seam-specific failure/unverified reason (not only "write a regression test against behavior that exists before the fix") and suggest: (a) base-portable observation (log/error/side effect that exists in production code after the fix but not before), or (b) seam-only base_patch, or (c) scaffold capture.
2. Add operator-controlled base_patch: --base-patch PATH (and/or settings) wired into autocode_regression.prove / verify like reviewed_patch, for new runs and resumes.
3. Update builder guidance (BUILDER_NOTE in tools/autocode_test_cases.py) so bugfix tests prefer base-portable production signals over a new injectable var solely for proving.

Tests: unit tests for seam detection (collection error names match added symbols); prove/verify accepts explicit base_patch; builder note text includes the guidance.

ISSUE #300 — Findings ledger blocks COMPLETE after a user decision already settled the same issue

Problem: tools/autocode_findings.py blocking_entries() and tools/autocode_completion.py completion_ready refuse COMPLETE while any row is blocking. Two findings with the same root cause: one resolved by permission_answer, one left open. Completion Owner queues bookkeeping tasks that do not clear the second row.

Required behavior:
1. When a finding is resolved (including by user permission_answer / feedback), auto-resolve other open blocking findings with the same root cause (same evidence path, same failure signature, or equivalent finding text).
2. A validate-only stage with changed_files empty must not be dispatched more than once in a row for the same open finding id; pause with a clear question instead.

Tests: findings controller/ledger tests for same-cause inheritance and bookkeeping cap.

ISSUE #301 — Operational recovery: external_directory, time caps, and grant-recovery maze

Problem: OpenCode external_directory denial, PAUSED_TIME_LIMIT (explicit_user_cap), and attempt exhaustion each need different flags. --grant-recovery is rejected except for PAUSED_TIMEOUT_RECOVERY. Raising --max-seconds does not always supersede a pending operational_exhaustion request in the same invocation.

Required behavior:
1. --resume-paused must either continue or print one concrete next command for this pause class (never suggest --grant-recovery when it will be rejected).
2. Explicit --max-seconds / --max-iterations on resume must supersede the operational request and continue in that invocation (no second Q&A).
3. Stage evidence/output paths must stay inside the run workspace (no /tmp) so OpenCode external_directory is not needed for runner-owned receipts. If a denial happens with no source change, retry with corrected instruction without consuming a timeout-recovery slot.

Tests: resume path unit/integration tests for each pause class message; supersede-on-budget-change; path confinement for stage evidence.

ISSUE #302 — Tree change during WAITING_FOR_USER leaves validation stale; completion cannot proceed

Problem: After tests/source change while paused, validation still has old source_revision / task_id / verdict. accept_completion fails; resume can raise PAUSED_STALE_GOAL when applying leftover stage values.

Required behavior:
1. On resume, if workspace revision != validation.source_revision, mark validation non-current and dispatch one fresh independent validation (sol / review) before completion.
2. accept-completion when validation is stale must say what to do (resume to re-validate) rather than only the generic evidence message.
3. Do not raise PAUSED_STALE_GOAL for recovered stage values whose contract_revision/task_id/source_revision are stale; discard them and schedule a fresh attempt. Archive pending_report_repair whose original.source_revision is not current.

Tests: completion_ready / accept_completion messaging; resume discards stale stage values; pending_report_repair archived on tree change.
